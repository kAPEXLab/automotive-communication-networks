# Problem Statement: Exploring SocketCAN: Software-Only CAN/CAN FD Communication on Linux

## Background

In many real-world projects, software development and testing begin before CAN hardware is available. Linux provides a framework called **SocketCAN** that enables CAN and CAN FD communication through standard networking concepts, allowing engineers to develop, test, monitor, and debug CAN-based applications entirely in software.

Your task is to investigate SocketCAN and build a small CAN-based application that demonstrates communication between multiple software nodes without using any external CAN hardware.

---

## Objective

Understand the SocketCAN framework and how it enables CAN/CAN FD communication on Linux.

Design and implement a working demonstration consisting of multiple software nodes that communicate over a CAN network using SocketCAN.

---

## Investigation Tasks

### Task 1: Understanding SocketCAN

Investigate and document:

- What is SocketCAN?
- Why is CAN treated as a network interface in Linux?
- How is SocketCAN different from vendor-specific CAN APIs?
- What advantages does this architecture provide?

**Deliverable:** 1-page summary document.

---

### Task 2: CAN Network Discovery

Investigate how Linux enables CAN communication without physical CAN hardware.

Study:

- Available CAN interface types
- How applications connect to a CAN network
- How multiple applications communicate simultaneously

**Deliverable:** Architecture diagram with explanation.

---

### Task 3: CAN Frame Exploration

Study the structure of a CAN frame and identify:

- Message Identifier (CAN ID)
- DLC (Data Length Code)
- Data Payload
- Standard vs Extended Identifiers

Create a signal mapping for the following data:

- Vehicle Speed
- Engine RPM
- Coolant Temperature

**Deliverable:** CAN message definition document.

---

## System Requirements

Develop a software solution containing the following nodes:

### Vehicle ECU

Transmits:

- Vehicle Speed (0-120 km/h)
- Engine RPM (800-5000 rpm)
- Coolant Temperature (20-120 °C)

The values should vary realistically over time.

---

### Dashboard ECU

Receives CAN messages and displays the decoded information.

Example:

```text
--------------------------------
Vehicle Dashboard
--------------------------------
Speed       : 65 km/h
Engine RPM  : 2450 rpm
Temperature : 88 °C
--------------------------------
```

The display should update continuously.

---

### Logger ECU

Records all observed CAN traffic.

Each log entry should contain:

- Timestamp
- Message Identifier
- Payload Length
- Payload Data

Store the information in a text or CSV file.

---

## Learning Challenges

### Challenge 1: Traffic Observation

Observe CAN traffic generated by the Vehicle ECU.

Answer the following:

- Can multiple applications observe the same traffic simultaneously?
- Does communication continue to work when the Logger ECU is active?
- What observations can be made about message delivery?

Document your findings.

---

### Challenge 2: Message Filtering

Modify the Dashboard ECU to perform the following:

1. Receive all messages.
2. Receive only Speed messages.
3. Receive only RPM messages.

Document the filtering approach and observations.

---

### Challenge 3: Unknown Message Detection

Introduce a new CAN message not originally defined in the system.

Verify:

- Is the message recorded by Logger ECU?
- Is the message displayed by Dashboard ECU?
- How does the system behave when receiving unknown messages?

Document your findings.

---

### Challenge 4: Transmission Rate Study

Experiment with different transmission rates.

Observe:

- Receiver behavior
- System responsiveness
- Log file growth
- Resource utilization

Document your observations and conclusions.

---

### Challenge 5: Node Failure Study

Terminate the Vehicle ECU while the Dashboard ECU and Logger ECU remain active.

Investigate:

- What is observed by Dashboard ECU?
- What is observed by Logger ECU?
- How can an application detect loss of communication?

Summarize your findings.

---

### Challenge 6: CAN FD Exploration

Extend the implementation to support CAN FD.

Investigate and document:

- Differences between CAN and CAN FD
- Payload size capability
- Application changes required
- Benefits of CAN FD

Demonstrate successful CAN FD communication.

---

### Challenge 7: Basic Diagnostics

Implement a simple diagnostic feature.

Example:

```text
If no Speed message is received for a specified duration,
display:

WARNING: Vehicle ECU Offline
```

Any equivalent diagnostic mechanism may be implemented.
